# 复盘：「文件面板报 session not found」

> 一次持续两天、六轮修复的排查。真正的修复只有一行条件判断；
> 值得记录的是为什么定位它花了这么久，以及由此固化的测试不变式。

## 现象

在应用的「远程环境」页里打开远端界面的文件面板，报：

```
session "session-…" not found
```

同一页面用浏览器直接打开完全正常。

## 时间线

| 轮 | 假设 | 改动 | 验证方式 | 结果 |
|---|---|---|---|---|
| 1 | 同源共享 localStorage，远端读到本地会话 id | 存储按环境命名空间 | 沙箱（http）比对存储键 | 沙箱过，线上不过 |
| 2 | 绝对路径请求绕过代理打到本地 | 注入 fetch/XHR/WS 改写 | 沙箱抓 performance entries | 沙箱过，线上不过 |
| 3 | 桌面 preload 冻结 fetch，补丁装不上 | defineProperty 优先 + 补丁状态上报 | vm 行为测试 | 线上仍失败 |
| 4 | （自身事故）PATCH 变量作用域错误 | — | 启动诊断被自身 catch 吞掉 | 整轮零数据 |
| 5 | 转为取证 | mux 帧遥测；经代理重放同会话 RPC | 远端 200；假 id 报一字不差的错 | 确认答复方是本地应用 |
| 6 | scheme 白名单过窄 | 协议判断改为与文档协议比较 | 新增 dsh-app:// 用例 | **修复** |

## 根因

远端界面用**绝对路径**发请求（如 `/sidebar/api/fs.trees`）。帧内改写函数
`toProxy` 只放行 `http/https/ws/wss` 协议，而桌面应用的页面是自定义协议
`dsh-app://app`——于是这些请求**原样放行**，直接打到本地 dsh；本地没有
远端会话，报 not found。

真正的教训不在这一行代码，而在三层系统性缺口：

1. **验证层**：测试环境（http 沙箱）与用户环境（dsh-app 桌面）在唯一关键
   维度上不同，"沙箱通过"结构性无效。
2. **观测层**：诊断代码活在被诊断的 try 块里，自身出错即静默（第 4 轮）。
3. **流程层**：连续多轮"假设→改→沙箱验证→让用户重启"，而不是两轮失败后
   转为一次性取证。

## 固化的测试不变式

这些用例都不是"多测一点"，而是每一条对应一层缺口：

| 不变式 | 防什么 | 位置 |
|---|---|---|
| 自定义协议（dsh-app://）文档下绝对路径必须被改写 | 环境矩阵缺口（本 bug 直接原因） | `frame-shim` |
| 注入脚本→代理→上游端到端：上游收到剥前缀的原始路径 + 注入的 cookie | 通道选择整链断裂 | `frame-shim` |
| 注入脚本自身出错必须上报 `frame-error` | 诊断静默消失（第 4 轮） | `frame-shim` |
| vm 测试捕获 console.error，吞错即全红 | 测试哑掉错误出口 | `frame-shim` |
| 启动诊断携带 patches 状态 | "补丁装没装上"不再靠猜 | `frame-shim` |

## 排查守则（写给以后的人，也写给以后的我们）

1. 同一问题两轮假设失败，停止改代码，转为一次性取证：
   出错调用的 endpoint、参数、通道、由谁答复。
2. 报错文案本身是证据：拿它去两端各自复现，谁吐出一字不差的文案谁就是答复方。
3. 环境差异先列矩阵（协议 / origin / 帧类型），逐格确认行为，再谈修复。
4. 诊断不能活在被诊断的代码里；失败也要上报。
5. 未在用户环境实测，不说"已修复"。
